1. 의사결정 요청

권고: 제출 자료 작성은 계속하되, 최종 심사 제출은 DPI 추가 검증과 PM의 잔여 위험 검토 후 진행한다. 이는 내부 품질 관리 제안이며, Microsoft가 모든 WARNING에 제출 금지를 요구한다는 뜻은 아니다.

개발 담당자는 DPI 분석 실패 원인 조사와 선택 검사 참조 분석을, QA 담당자는 화면 배율·실제 기능 확인과 WACK 재검사를 맡는다. PM은 담당자를 지정하고 검증 결과에 따라 수정 후 제출 또는 근거를 첨부한 제출을 결정한다. 한 사람이 역할을 겸할 수 있다.

이번 요청은 조사·검증·필요한 수정에 대한 요청이다. Store 제출 승인이나 출시 완료 보고가 아니다. 구체적인 수정 범위와 일정은 1차 재현 결과를 확인한 뒤 산정한다.

3. FR-01 — DPI 분석 경고 조사 및 화면 배율 검증

우선순위 제안: 높음 / 담당: 개발 + QA / 현재 상태: 미해결

발생 현상
필수 항목 DPIAwarenessValidation이 WARNING이다. 보고서에는 설치된 실행 파일을 처리하지 못했다는 메시지와 DPI 미인식 메시지가 함께 기록되어 있다.

확인된 증거
• 앱 매니페스트에 PerMonitorV2, true/pm, asInvoker가 선언되어 있다.
• WindowsApps 설치 경로에서 분석기의 IsPerMonitorV2DPIAwarenessSet 호출이 E_FAIL을 반환했다.
• SHA256이 동일한 EXE를 작업 폴더와 공백이 포함된 일반 폴더에 복사하면 같은 분석기가 true를 반환했다.
• 설치된 앱의 실제 메인 창은 PerMonitorV2로 확인되었고 시작·응답성 검사도 통과했다.

아직 확인되지 않은 것
설치 경로에 따라 분석 결과가 달라지는 세부 원인은 확정하지 않았다. 도구·접근 조건의 영향이 의심되지만 ‘WACK 버그’ 또는 ‘오탐’으로 확정해서는 안 된다. 실제 실행의 DPI 모드 확인만으로 화면 잘림·다중 모니터 이동까지 검증되지는 않는다.

요청 작업
① 기존 원본 보고서, 분석 로그, 실행 파일 해시, OS·SDK·WACK 버전을 보존한다.
② 유효한 로컬 테스트 서명 환경을 준비하고 원본 페이로드가 유지된 시험 패키지를 설치한다.
③ 동일 환경에서 설치 경로와 일반 경로의 분석 결과를 다시 비교한다. 파일 해시, 실행 권한, 분석기 버전 등 조건을 기록한다. WindowsApps 권한을 임의로 변경하지 않는다.
④ 가능하면 별도 깨끗한 Windows 환경에서 같은 패키지로 재현한다. 환경을 바꿀 때는 변수를 한 번에 하나씩 바꾼다.
⑤ QA가 100%·150%·200% 배율에서 메인 화면·설정 창·파일 선택·오류 표시·하단 버튼의 잘림, 겹침, 조작 가능 여부를 확인한다. 다중 모니터 지원을 표방하려면 배율이 다른 모니터 간 이동도 확인한다. 장비가 없으면 미실시로 기록한다.
⑥ 앱 결함이 확인되면 수정·버전 증가·새 MSIX 생성 후 관련 기능 검사와 전체 WACK를 다시 실행한다. 기존 1.0.2.0 파일을 같은 이름으로 덮어쓰지 않는다.
⑦ 앱 결함이 재현되지 않고 분석기 경고만 남으면 최소 재현 절차와 증거를 정리해 Microsoft 개발자 지원에 문의하고, PM에게 남은 위험을 보고한다.

완료 기준
• 경로별 분석 비교와 배율별 실사용 결과가 문서화되어 있음.
• 실제 화면 결함이 있으면 수정 후 재검증 완료.
• 전체 WACK 재검사 결과 및 원본 보고서 확보.
• PASS가 되면 해소로 종결. WARNING이 남으면 ‘해결’로 닫지 않고 ‘잔여 위험 검토’로 전환하며, PM이 제출 여부와 근거를 기록.

4. FR-02 — 선택 검사 ‘차단된 실행 파일’ 참조 분석

우선순위 제안: 중간 / 담당: 개발 / 현재 상태: 분석 근거 보강 필요

발생 현상
선택 항목 ‘차단된 실행 파일’이 FAIL이다. .NET/WPF 구성 파일 및 앱 호스트에서 CreateProcessW, Process.Start, ShellExecute 계열 API와 cmd 등의 문자열 참조가 검출되었다.

확인된 증거와 한계
기존 소스 검색에서는 앱 자체가 직접 외부 프로세스를 시작하는 코드를 발견하지 못했다. 그러나 문자열·API 참조의 존재만으로 실제 실행 여부를 확정할 수 없고, 단순 소스 검색만으로 모든 런타임 동작의 부재를 입증할 수도 없다.

Microsoft는 Desktop Bridge 선택 검사를 참고 정보로 설명하며, 이 선택 검사 결과 자체는 Store 온보딩의 통과·실패 판단에 사용하지 않는다고 명시한다. 필수 DPI 경고와는 별개로 관리한다. 실제 부적절한 외부 실행 동작이 있다면 선택 항목이라는 이유로 무시하지 않는다. [출처 1]

요청 작업
① 검출 항목 전체를 파일명·API/문자열·파일 출처·앱에서의 사용 여부로 분류한다.
② 앱 자체 코드, 패키지 구성, 주요 사용자 동작에서 외부 프로세스 실행 의존성이 있는지 확인한다. 필요하면 승인된 개발 진단 도구로 프로세스 생성 동작을 기록한다.
③ 불필요한 실제 외부 실행이 발견되면 제거하거나 정상적인 구현으로 변경하고 재검증한다.
④ 런타임 내부 참조로 판단되는 항목은 근거를 남긴다. 사용하지 않는 배포 파일의 제외는 의존성과 설치·실행 회귀 검증을 통해 결정하며, FAIL을 없애려고 런타임 DLL을 임의 삭제하지 않는다.
⑤ 분석 결과를 심사 메모에 사실대로 반영한다. ‘오탐 확정’, ‘완전 통과’라고 표현하지 않는다.

완료 기준
검출 항목 분류표, 실제 외부 실행 의존성 검토 결과, 필요 시 수정·회귀 결과를 확보한다. 선택 FAIL이 남아도 실제 결함이 없다는 근거와 관리 방침이 정리되면 정보성 항목으로 추적할 수 있다. 전체 결과를 PASS로 바꾸거나 원본 로그를 수정하지 않는다.

5. FR-03 — 로컬 재검사 인증서 준비

우선순위 제안: 재검사 선행 작업 / 담당: 빌드·개발

기존 임시 테스트 인증서는 2026-11-20 00:28:44 한국시간에 만료되었다. 11월 24일 현재 새 설치·서명 검증에 그대로 사용하면 문제가 생길 수 있으므로 유효한 테스트 인증서와 서명 사본을 준비한다.

• Store 제출용 Release 원본은 보존하고 테스트용 사본에만 임시 서명한다.
• 원본과 테스트 사본의 페이로드 동일성을 확인하고 각각의 해시를 기록한다.
• 필요한 인증서 신뢰 설정은 허가된 시험 환경에서만 수행한다.
• 임시 인증서·개인 키를 고객 배포물이나 PM 첨부물에 넣지 않는다.

임시 테스트 인증서 만료는 Store 제출용 원본 MSIX가 만료됐다는 뜻이 아니다. Microsoft Store는 배포 시 MSIX/AppX에 서명하므로 Store 배포를 위해 별도 유료 인증서를 구매하는 작업은 이번 조치에 포함하지 않는다. [출처 2]

6. PM 작업 배정 및 제출 판단

진행 순서
A. 개발: 증거 보존 → 테스트 서명 준비 → DPI 재현 조사
B. 개발: 선택 FAIL 검출 항목 분석(배율 QA와 병행 가능)
C. QA: 설치된 앱의 배율·다중 모니터·파일 변경·되돌리기·충돌 방지·끌어 놓기·설정 복원 점검
D. 개발·QA: 필요한 수정 → 버전 관리 → 최종 후보 전체 WACK 재검사
E. PM: 결과와 잔여 위험 검토 → 심사 메모 확정 → 제출 승인 여부 결정

제출 보류 조건
• 실제 화면 조작 불가·파일 처리 오류 등 사용자 기능 결함이 남아 있음.
• 최종 후보에 필수 FAIL 또는 검사가 완료되지 않은 상태가 있음.
• 제출 파일과 시험 파일의 버전·페이로드 관계가 확인되지 않음.
• 경고를 설명할 증거가 부족하고 검증 범위가 불명확함.

조건부 제출 검토 조건
• 실제 기능·화면 배율 검증에 통과하고 필수 FAIL이 없음.
• 전체 WACK 실행이 완료되었으며, 남은 경고와 선택 FAIL의 근거·한계가 정리됨.
• PM이 미실시 항목과 반려 가능성을 검토하고 제출 결정을 기록함.
• 심사 메모에 원본 판정과 재현 근거를 명시함.

조건부 제출은 Microsoft의 사전 승인이나 심사 통과 보장이 아니다. 심사 결과에 따라 추가 수정이 필요할 수 있다.
