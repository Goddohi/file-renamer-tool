# 처음 만든 앱을 배포하는 준비 가이드

작성·공식 문서 확인: 2026-11-16. 사례: File Renamer 1.0.2.0, Windows 데스크톱 앱, Microsoft Store MSIX 배포.

이 문서는 앱을 처음 출시하는 사람이 순서대로 따라 쓰는 작업 안내입니다. 1~3장은 이번 앱에서 할 일이고, 4장부터는 다음 앱에도 복사해서 사용할 수 있습니다. 웹·모바일 앱에도 기획·테스트·소개 자료·출시 후 점검 순서는 적용되지만, 설치 파일과 심사 절차는 해당 플랫폼에 맞춰 바꿔야 합니다.

## 2. 이번 앱은 어디까지 준비됐나

아래 상태는 저장소의 2026-11-13 검증 기록을 기준으로 작성했습니다. 11월 16일에는 제출 후보 파일이 존재하며 기록된 SHA256과 일치하는 것을 다시 확인했습니다. Partner Center의 현재 화면은 이번 가이드 작성 중 직접 열어 확인하지 않았습니다.

| 항목 | 확인된 상태 | 아직 필요한 일 |
| --- | --- | --- |
| 제품 식별자 | 기존 기록에 Name·Publisher·Store ID 있음 | Partner Center의 실제 제품과 다시 대조 |
| 제출용 파일 | 1.0.2.0 x64 MSIX 생성, MakeAppx 검증 완료 | 최신 파일을 업로드 |
| 자동 기능 테스트 | Core 테스트 125개 통과 기록 | 이후 기능을 수정하면 관련 테스트 재실행 |
| 최종 패키지 설치 | 1.0.2.0 설치 및 시작 응답성 확인 | 최종 버전에서 실제 사용 흐름 한 번 더 확인 |
| 이전 버전의 주요 기능 | 이름 변경, 되돌리기, 충돌 방지, 설정 저장 확인 | 이전 결과를 최종 버전 전체 기능 검증으로 대신하지 않기 |
| DPI 동작 | 실제 창의 PerMonitorV2 확인 | 100%·150%·200% 및 다른 배율의 모니터에서 시각 확인 |
| 드래그 앤 드롭 | 수동 검증 미완료 기록 | 일반 권한으로 실행한 앱에 탐색기 파일을 끌어 놓기 |
| WACK | 24개 중 22 PASS, 선택 1 FAIL, 필수 DPI 1 WARNING | 경고와 재현 근거를 보존해 심사 메모에 설명 |
| 소개·스크린샷·지원 정보 | 최종 등록 자료 완성 여부 확인 필요 | 아래 초안과 촬영 목록 사용 |
| Store 제출 | 저장소 기록상 미업로드·미제출 | 초안 작성 → 검토 → 심사 제출 |

**WACK 결과는 완전 통과가 아닙니다.** 필수 검사 중 FAIL은 없지만 DPI WARNING이 남아 있습니다. 동일한 EXE가 일반 폴더에서는 DPI 분석에 성공하고 WindowsApps 설치 경로에서는 E_FAIL을 반환했습니다. 실제 실행 창은 PerMonitorV2입니다. 도구의 경로별 분석 차이를 재현한 것이며, 이 사실만으로 Microsoft 심사 통과를 보장하지는 않습니다.

선택 검사인 ‘차단된 실행 파일’은 포함된 .NET/WPF 및 앱 호스트의 API·문자열 참조를 표시했습니다. Microsoft는 Desktop Bridge의 선택 검사를 참고 정보로 설명합니다. 다만 다른 앱에서는 실제로 외부 프로그램을 실행하는 코드가 원인일 수 있으므로, 같은 경고가 나왔다고 무조건 무시하면 안 됩니다. [필수·선택 검사 구분](https://learn.microsoft.com/en-us/windows/uwp/debug-test-perf/windows-desktop-bridge-app-tests)

## 3. Partner Center에서 하나씩 진행하기

화면의 언어·계정·제품 유형에 따라 이름과 배치가 달라질 수 있습니다. ‘필수’ 표시는 실제 제출 화면에서도 확인하세요.

1. [Partner Center](https://partner.microsoft.com/dashboard)에 로그인합니다. 이전에 앱 이름을 예약한 계정을 사용합니다.
2. 앱 목록에서 `File Renamer_Dohi`를 선택합니다. 저장된 Store ID는 `9PF0VRZBLG81`입니다. 다른 제품을 선택하지 않았는지 확인합니다.
3. 제품 개요에서 **제출 시작 / Start submission**으로 초안을 만듭니다. 이미 초안이 있으면 그것을 엽니다. [제출 초안 만들기](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/create-app-submission)
4. **패키지 / Packages**에서 위의 1.0.2.0 MSIX를 업로드합니다. 검증이 끝날 때까지 기다리고 이름·게시자·버전·지원 기기 오류를 확인합니다. ‘파일 검증 완료’와 ‘패키지 섹션 작성 완료’는 다를 수 있습니다. 남은 필수 설정도 채웁니다. [패키지 검증 안내](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/upload-app-packages)
5. **가격 및 공급 / Pricing and availability**에서 결정표의 가격과 국가를 설정합니다. 첫 출시 범위가 의도보다 넓지 않은지 확인합니다.
6. **속성 / Properties**에서 카테고리와 지원 정보를 입력합니다. 이 앱은 생산성·유틸리티 계열을 검토하되 실제 선택지와 기능에 맞춰 고릅니다. 개인정보 접근·수집·전송 여부는 실제 동작대로 답합니다. 필요할 때는 유효한 개인정보처리방침 URL이 요구되며 선언한 권한에 따라 추가 요구가 생길 수 있습니다. [앱 속성과 개인정보 안내](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/enter-app-properties)
7. **연령 등급 / Age ratings** 질문에 답하고 결과를 생성·저장합니다. ‘사무용이니 전체 이용가’처럼 직접 추정해서 정하는 것이 아니라 실제 콘텐츠와 기능에 대한 설문에 답합니다. [연령 등급 설문](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/age-ratings)
8. **Store 목록 / Store listings**의 한국어 항목에 소개문과 스크린샷을 넣습니다. 앱이 실제 지원하지 않는 언어를 지원한다고 쓰지 않습니다.
9. **제출 옵션 / Submission options**의 심사 메모에 사용법, `runFullTrust` 이유, 이번 WACK 결과를 적습니다. 아래 초안에서 사용하지 않는 내용을 제거한 뒤 넣습니다. [심사 메모 및 제출 옵션](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/manage-submission-options)
10. 모든 필수 항목을 저장하고 미완료 표시를 해결합니다. 자동 공개인지 수동 공개인지 확인한 뒤 심사를 제출합니다. 수동 공개를 원한다면 제출 전에 해당 게시 보류 옵션을 선택합니다. 심사 통과 후 기본 설정에 따라 게시가 이어질 수 있습니다. [심사와 공개 단계](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-certification-process)

업로드 오류가 나면 **오류 문구 전체, 업로드한 파일명, 화면의 항목 이름**을 기록하세요. 파일을 임의로 고치거나 인증서를 새로 사기 전에 어떤 값이 맞지 않는지부터 확인합니다.

### 실제 화면 캡처 준비

MSIX 데스크톱 목록은 최소 1장, Microsoft 권장 수량은 4장 이상입니다. PNG 형식, 각 파일 50MB 이하, 데스크톱 기준 1366×768 이상을 준비합니다. 1920×1080은 준비하기 편한 예시 크기입니다. 실제 화면을 읽기 어려울 정도로 늘리거나 가상의 기능을 합성하지 마세요. [공식 스크린샷 기준](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/screenshots-and-images)

이번 앱에는 다음 네 장을 제안합니다.

| 장면 | 예시 데이터 | 보여줄 내용 |
| --- | --- | --- |
| 찾아 바꾸기 | `보고서_초안.txt` → `보고서_최종.txt` | 변경 전후 미리보기 |
| 순번 | `사진_001.jpg`, `사진_002.jpg` | 여러 파일의 순서와 번호 지정 |
| 템플릿 | `20261116_샘플회사_견적서_홍길동.xlsx` | 날짜·회사명·이름 조합 |
| 충돌 방지 또는 다크 모드 | 같은 이름이 되는 예시 파일 | 오류 안내 또는 화면 설정 |

촬영에는 복사본과 가상 이름을 사용합니다. 개인 파일 경로, 실제 고객명, 이메일, 사용자 계정명, 알림이 보이지 않는지 확인하세요. 앱 내부 아이콘을 만들었다고 Store 스크린샷도 준비된 것은 아닙니다.

촬영 순서는 ‘예시 파일 추가 → 보여줄 기능 선택 → 앱 창을 충분히 크게 열기 → Windows 캡처 도구로 앱 화면 저장 → PNG 크기와 개인정보 확인’입니다. 작은 창을 찍은 뒤 확대해서 규격만 맞추면 글자가 흐려질 수 있으므로 처음부터 충분한 크기로 촬영합니다. 파일명은 `01-미리보기.png`, `02-순번.png`처럼 순서를 알아볼 수 있게 붙입니다.

### 소개문 초안

아래 문구는 현재 구현된 기능을 바탕으로 만든 초안입니다. 실제 출시 버전을 사용해 본 뒤 확정하세요.

> File Renamer는 여러 파일의 이름을 한 번에 정리하는 Windows용 도구입니다. 찾아 바꾸기, 템플릿, 대소문자 변환, 순번 매기기를 지원하며 변경 전후 이름을 미리 확인할 수 있습니다. 중복 이름과 사용할 수 없는 문자를 검사하고, 마지막 이름 변경 작업을 한 번 되돌릴 수 있습니다. 날짜·회사명·이름을 조합하는 템플릿과 일반·다크 화면 모드를 제공합니다. 파일 확장자는 유지됩니다.

‘어떤 파일이든 절대 손상 없음’, ‘모든 PC에서 완벽’, ‘인증 완료’처럼 검증 범위를 넘는 표현은 넣지 않습니다.

### 지원·개인정보 안내에 넣을 사실

이름 변경 앱도 파일명·경로에 접근합니다. 현재 코드에는 회사명·사용자 이름·최근 입력값·테마를 로컬 설정에 저장하는 기능이 있습니다. 따라서 ‘어떤 정보도 저장하지 않는다’라고 쓰면 실제 동작과 다릅니다.

공개 안내문을 만들 때 다음 내용을 확인하고 적습니다.

- 운영자 또는 개발자 이름과 문의 연락처
- 앱이 다루는 정보: 선택한 파일명·경로, 사용자가 입력한 설정 등
- 처리 목적: 파일 이름 변경, 미리보기, 설정 복원 등
- 저장 장소와 외부 전송 여부: 앱 코드뿐 아니라 분석·오류 수집 SDK도 확인
- 보관·삭제 방법: 실제 설치 환경에서 확인한 설정 초기화 또는 삭제 방법
- 적용일과 변경 안내 방법

코드의 설정 경로 기준은 `%AppData%\FileRenamer\settings.json`입니다. MSIX 설치 환경에서는 Windows의 앱 데이터 처리 방식도 고려해 실제 위치를 확인한 뒤 삭제 방법을 안내하세요. 문의 이메일로 받는 정보와 Microsoft Store 자체 처리는 앱 내부 처리와 구분합니다. 로그인 없이 열리는 안내 URL을 준비하면 제출과 사용자 안내에 활용할 수 있습니다. 필요한 정책의 범위는 위 공식 속성 안내와 실제 데이터 처리에 맞춰 확인합니다.

## 4. 다음 앱에도 쓸 수 있는 준비 순서

### 1단계 — 누구에게 무엇을 제공할지 정하기

한 문장으로 ‘누가, 어떤 문제를, 이 앱으로 해결하는가’를 적습니다. 이어서 지원 기기·OS·언어, 무료/유료, 핵심 기능 세 가지를 정합니다.

**남길 것:** 앱 설명 한 문장과 출시 범위. 기능이 추가될 때마다 이번 버전에 꼭 필요한지 판단하는 기준이 됩니다.

### 2단계 — 배포 방식과 제품 이름 정하기

Windows 앱이라면 Store의 MSIX 배포인지, 직접 내려받는 EXE/MSI인지 먼저 구분합니다. 배포 방식에 따라 설치·서명·업데이트 방법이 달라집니다. Store 제품을 만들면 제품 식별자와 게시자 정보를 따로 기록합니다.

**남길 것:** 표시 이름, 제품 ID, 게시자, 지원 환경 표. 다른 앱을 만들 때 File Renamer의 Name·Publisher·Store ID를 그대로 복사하지 않습니다.

### 3단계 — 실제 기능과 예외 상황 확인하기

개발 화면에서 실행되는 것과 사용자가 설치해서 쓰는 것은 다릅니다. 정상 입력뿐 아니라 빈 입력, 중복, 잘못된 형식, 접근 권한 없음, 중간 취소도 확인합니다.

**남길 것:** ‘어떤 입력 → 어떤 결과’를 적은 테스트 기록. 파일이나 데이터를 변경하는 앱이라면 시험용 데이터로 내용 보존과 복구를 확인합니다.

### 4단계 — 배포 파일 만들기

사용자용 빌드인 Release를 만들고 버전 번호를 붙입니다. 필요한 실행 환경을 포함할지, 별도로 설치하게 할지 정합니다. 패키지 안에 설정 비밀값, 개인 키, 개발 중 임시 파일이 들어가지 않게 확인합니다.

**남길 것:** 배포 파일, 버전, 빌드 방법, 파일의 SHA256. SHA256은 파일이 같은지 비교하는 지문이며 안전성을 보증하는 인증서는 아닙니다.

### 5단계 — 설치된 앱으로 확인하기

개발 도구가 없는 별도 PC나 깨끗한 테스트 환경에서 새 설치를 확인합니다. 업데이트가 있는 앱은 이전 버전 위에 설치했을 때 설정과 데이터가 유지되는지도 봅니다.

**남길 것:** OS·버전·기기 종류, 새 설치/업데이트/실행 결과. x64에서만 확인했다면 ARM64에서도 검증했다고 쓰지 않습니다.

### 6단계 — 인증 검사와 원인 구분하기

플랫폼의 검사 도구를 실행하고 원본 보고서를 보관합니다. 검사 명령이 종료됐다는 이유만으로 합격이라고 판단하지 않습니다. 테스트 실행 여부, 전체 판정, 각 항목의 경고와 실패를 읽습니다.

| 결과 | 뜻 | 다음 행동 |
| --- | --- | --- |
| PASS | 해당 검사가 통과됨 | 어떤 버전으로 확인했는지 저장 |
| WARNING | 추가 확인이 필요한 내용이 있음 | 실제 동작·오류 근거를 확인하고 설명 |
| FAIL | 해당 검사가 실패함 | 필수/선택 여부와 원인 확인 후 수정 또는 근거 정리 |
| 미실행·부분 실행 | 검사가 충분히 수행되지 않음 | 설치·권한·도구 환경을 해결한 뒤 재실행 |

‘도구 오류 같다’는 추측만으로 넘기지 않습니다. 동일 파일 비교, 실제 실행 결과, 상세 오류 로그처럼 재현 가능한 근거가 필요합니다. 앱 코드를 바꿨다면 새 파일로 관련 검사를 다시 합니다.

### 7단계 — 사용자가 볼 설명과 이미지를 만들기

소개문은 ‘무엇을 할 수 있는가’를, 스크린샷은 ‘실제로 어떻게 보이는가’를 보여줍니다. 지원 환경, 제한 사항, 문의 경로, 데이터 처리 안내도 준비합니다.

**남길 것:** 소개문, 기능 목록, 실제 스크린샷, 지원·개인정보 URL, 필요한 라이선스·저작권 표시. 로그인·결제·광고·외부 API가 있는 앱은 관련 흐름도 추가로 확인합니다.

### 8단계 — 제출 초안과 공개 설정 확인하기

배포 파일과 설명을 등록한 뒤 가격·국가·공개 범위·연령 등급·게시 시점을 마지막으로 확인합니다. 앱 파일을 업로드한 것과 심사를 제출한 것, 실제로 공개된 것은 서로 다른 상태입니다.

**남길 것:** 제출 버전, 제출일, 선택한 가격과 국가, 공개 방식, 경고에 대한 심사 설명.

### 9단계 — 심사 결과 대응하기

반려되면 보고서의 항목과 재현 절차를 먼저 읽습니다. 앱 문제면 수정하고 버전을 올려 다시 검사합니다. 설명이나 자료 문제면 해당 내용을 수정합니다. 이미 확인한 부분을 이유 없이 전부 다시 만들지 않습니다.

### 10단계 — 공개된 제품을 다시 설치해 보기

Store에서 일반 사용자처럼 내려받아 실행하고, 소개와 실제 기능이 같은지 확인합니다. 문의 대응 경로가 작동하는지 점검하고 다음 수정 사항을 기록합니다.

**남길 것:** 공개 링크, 실제 설치 확인, 알려진 문제, 다음 버전 계획. 이후 업데이트도 변경한 기능과 설치·업데이트 흐름을 중심으로 같은 순서를 반복합니다.

## 8. 개발 명령이 필요할 때

이 절의 명령은 **현재 File Renamer 저장소 전용**입니다. 다른 프로젝트에 그대로 쓰지 마세요. 현재 1.0.2.0 파일은 이미 있으므로 업로드를 위해 다시 빌드할 필요는 없습니다.

다음 변경을 만든 뒤 새 후보를 빌드하는 예시입니다. `1.0.3.0`은 다음 버전의 예시일 뿐 지금 만들어져 있는 파일이 아닙니다.

```powershell
dotnet test FileRenamer.sln -c Release
dotnet msbuild packaging/FileRenamer.Package.proj /t:Build /p:PackageVersion=1.0.3.0
```

이 프로젝트의 패키징 기본 버전은 아직 1.0.0.0이므로 **버전 옵션을 생략하지 마세요.** 버전별 테스트 서명 사본은 `New-TestPackage.ps1 -Version ... -TestRoot ...`로 별도 폴더에 준비할 수 있습니다. 기존 테스트 앱이 설치돼 있으면 설치 스크립트가 의도적으로 중단하므로, 업데이트와 새 설치를 구분해 개발 담당자에게 맡기세요. 설치 기록을 삭제해서 보호 장치를 우회하지 않습니다.

현재 설치된 후보에 대해 WACK를 다시 실행하려면 관리자 PowerShell에서 저장소 위치로 이동한 뒤 아래 명령을 사용합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File packaging/Test-Wack.ps1
```

이 스크립트는 WARNING도 오류로 반환합니다. 반환 코드만 보고 검사가 실행되지 않았다고 판단하지 말고 새 폴더의 `report.xml`과 `summary.json`을 읽으세요. 또한 이미 검증한 패키지 대신 다른 버전이 설치돼 있지 않은지 먼저 확인합니다.
